# Event-note reconciliation risk register

This register captures the implementation boundary for explicitly linked Google Calendar series, occurrence, and occurrence-day notes. The approved work packages and acceptance status are in the [event-note reconciliation implementation plan](event-note-reconciliation-plan.md); the broader calendar handoff remains in [SYNC_IMPLEMENTATION_PLAN.md](../SYNC_IMPLEMENTATION_PLAN.md). The “Current behavior” column records the checkout before implementation. Note creation remains explicit; notes remain attached to the Google-event projection, their Markdown bodies remain local, and Google event frontmatter does not write back to Google in this phase.

## 1. Problems and current behavior

| Area | Current behavior and evidence | Risk for linked recurrence notes |
| --- | --- | --- |
| Identity and cardinality | `CalendarEventRepository` indexes one note by `calendar_uid` and path. `createLinkedNote()` deduplicates by provider/account/calendar/remote event ID. `SyncService` stores a single `noteUid` and `notePath` on each cached remote event. | A series note, an occurrence note, and several day notes cannot be distinct targets of one recurring series. A note keyed by the event's current date or file path will silently detach when the instance moves or the file is renamed. |
| Recurrence representation | `CalendarEvent` carries a limited RRULE value, but `GoogleEventMapper` treats resources with `recurringEventId` as unsupported. `GoogleCalendarProvider` pulls with `singleEvents=false`, emits `series-unsupported` for exceptions, and maps `originalStartTime` nowhere. `SyncService.markSeriesUnsupported()` marks the master unsupported when exceptions are seen. | The current model cannot identify which recurrence slot an exception modifies. It cannot distinguish a moved occurrence from a new event by comparing only current dates, nor support an instance edit safely. Google defines `originalStartTime` as the immutable slot identity even when an instance is moved; `recurringEventId` points to its master. See [Google recurring events](https://developers.google.com/workspace/calendar/api/guides/recurringevents) and the [Event resource](https://developers.google.com/workspace/calendar/api/v3/reference/events). |
| Note ownership and projection | Inbound events populate `SyncState.remoteEvents`; sync does not create notes automatically. `DayDetailView` offers one Create/Open note action per cached event and excludes paths linked to displayed events from its generic Notes list. A prior dated-note prototype was rolled back after notes appeared as independent Notes. | Occurrence/day notes need a many-notes-to-series projection and must remain event-owned. Filtering only one `notePath` per event will leave additional day notes visible as ordinary dated notes or make them unreachable. Orphaned links must also remain recognizable as event notes. |
| Whole occurrence versus day notes | The repository has no occurrence target or representation-mode field and no exclusivity check. | A multi-day occurrence could end up with both one whole-occurrence note and notes for some of its days. Concurrent clicks or retries could also create duplicate notes. This violates the approved rule that one occurrence uses the whole-occurrence note or selected day notes, never both. |
| Recurrence edits, re-anchor, and split | Current cache keys are remote event IDs. The adapter retains raw recurrence lines for unsupported masters but does not model split-series relationships or per-slot identity. | Editing a series start can change the generated date slots; “this and following” can create a second master. Matching by title/date risks assigning old notes to the wrong series or occurrence. Missing identities need an explicit warning and reconciliation action, not automatic reassignment. |
| Exceptions and cancellation | Google exception resources carry a separate event ID, `recurringEventId`, `originalStartTime`, and may be `cancelled`. The adapter currently converts cancellation to a generic delete by event ID; the note model has no target scope to limit its effect. | A cancelled occurrence must mark only notes for that occurrence as remote-deleted and preserve their bodies. It must not delete or detach the series note or sibling occurrence/day notes. A moved exception must keep its original slot identity while displaying its new time. |
| Multi-day ranges and day offsets | Canonical all-day ends are exclusive. Native `dateEnd` frontmatter is inclusive. Current note metadata represents an event range, not an individual day target. | Day-note identity and range length must use civil days, not elapsed 24-hour blocks. When a range moves, day notes should follow their selected offset. If it shrinks past a selected offset, that target no longer exists and needs reconciliation; expansion must not create notes automatically. |
| Timezone and DST | Timed canonical values require RFC 3339 offsets plus an IANA timezone; recurring events are interpreted in the event timezone. A single event's displayed offset can differ from its recurrence timezone across DST. | Using UTC dates, fixed millisecond offsets, or the current event start as occurrence identity can shift day notes across DST or detach them after an exception move. All-day exclusive-end conversion can add or lose a visible day if mixed with local-time arithmetic. |
| Cursor, horizon, and partial results | Google sync uses `events.list` with `syncToken`, `showDeleted=true`, and `singleEvents=false`; the adapter follows pages and returns the final sync token. The engine persists changes and cursor state, performs full-cache initialization/reconciliation, and applies the configured horizon at the cache boundary. | Occurrence expansion must not corrupt the event cursor or turn “outside horizon” into “deleted.” A failure halfway through expansion or note reconciliation must be replay-safe. `events.list` has query-parameter restrictions with `syncToken`; do not bolt date-window expansion onto the incremental query without checking the API contract. See [Events: list](https://developers.google.com/workspace/calendar/api/v3/reference/events/list) and [pagination](https://developers.google.com/workspace/calendar/api/guides/pagination). |
| Offline, retry, stale version, and partial writes | The engine retries retryable provider errors, stores cached remote events independently of notes, uses event versions, and maps Google 412 responses to conflicts. Frontmatter writes use `processFrontMatter`; plugin state and vault files are persisted separately. | A retry after a note create/state-save interruption must find the same target and finish linking instead of creating another note. A stale ETag must not be retried blindly with an old event body. If one persistence step fails, surface repair status and retain enough target identity to recover on the next sync. |
| Rename, copy, duplicates, and invalid frontmatter | `calendar_uid` is immutable and the index reports duplicate UIDs. Provider association is frontmatter metadata; reload reports malformed event notes. A rename can refresh the stored path from the UID, while a copied file can duplicate its UID or provider reference. | Paths cannot be identity. Duplicate UID or target metadata must not cause a random winner or overwrite. Invalid metadata must not be interpreted as a new unlinked note and rebound by title/date. Show both conflicting paths and give a repair/relink path. |
| Migration and account/calendar changes | Plugin sync state is schema version 2 and existing note frontmatter stores one provider reference (`account_id`, `calendar_id`, `event_id`). Disconnect intentionally removes sync state while preserving notes/events. | Existing one-note links need deterministic classification. Account/calendar moves or “move to another calendar” operations change provider identity and must require manual relink. Never infer continuity from matching title, date, or filename; never delete a note during migration or disconnect. |
| UX and mode gates | Sync modes are `disabled`, `dry-run`, `import-only`, and `bidirectional`. Event actions live in the day-detail event cards; direct provider writes are gated to bidirectional desktop sync. | Create/open actions must target the selected series, occurrence, or day. Instance edits must address the exception instance. Import-only can display/cache events and create/open local notes but cannot write Google. Disabled/dry-run must not create notes or mutate provider data. Warnings must explain cancellation, a missing target, a duplicate, and a required manual relink. |

## 2. Resolution and test matrix

### Required resolution rules

1. **Use a provider target key independent of filenames and displayed dates.** Scope every target by provider, account, and calendar. A series key adds the recurring master event ID. An occurrence key adds the master ID and `originalStartTime` (date for all-day series; the recurrence-local timestamp/timezone for timed series). Use an occurrence's remote exception ID only to address provider writes, not as its stable slot identity. An occurrence-day key adds a zero-based civil-day offset from that occurrence's current local start. A non-recurring event uses its remote event ID as its occurrence identity.
2. **Enforce one note per target and one representation mode per occurrence.** A single target may resolve to only one `calendar_uid`. For each multi-day occurrence, either create one whole-occurrence note or one note for each explicitly selected day; reject the other mode until the user explicitly converts or removes the existing representation. Serialize creation by target key and make retries idempotent.
3. **Keep all target notes owned by the event projection.** Add a target-aware read model that can return a series note, an occurrence note, or day notes without making them ordinary Notes. The projection must hide every attached target note from the generic dated-note list, including when an occurrence disappears from the current horizon. Orphaned notes remain event notes with a visible reconciliation state.
4. **Generate readable dated names, then treat paths as locations only.** Use the target's displayed local date and event title for a new filename, with a collision-safe user-visible resolution. Renames and title changes do not change the target key or silently rename a file. A copied file or duplicate UID/provider target produces a warning with both paths; neither copy is selected automatically.
5. **Preserve target identity through event changes.** A moved exception stays attached through `(master ID, originalStartTime)` and its note's displayed event fields follow the new actual start/end. A series re-anchor retains a series note only while the master ID remains the same. A split/new master, missing original slot, calendar move, or account move raises reconciliation; keep affected notes and do not reassign them by similarity. A cancelled occurrence marks only its own target notes remote-deleted. A parent cancellation marks the series target and warns about child targets; it does not delete notes.
6. **Use day offsets as suggestions, not automatic reassignments.** Calculate offsets using event-local civil dates. If the occurrence moves, preview the corresponding new local date and retain the recorded association until the user confirms it. If the occurrence shrinks so that an offset is outside its exclusive-end range, preserve the note and flag it for manual resolution. A range extension creates no additional notes. Changing from whole-occurrence to day mode (or back) requires explicit conversion and a preview of affected notes.
7. **Keep linked-note frontmatter inbound-only in this phase.** Store local target metadata alongside the existing Google association; keep note bodies and unrelated frontmatter intact via `processFrontMatter`. The explicit event/instance edit action writes to Google in bidirectional mode with the current instance ID and ETag. Frontmatter edits do not write event fields back until a later outbound-frontmatter phase is designed and approved.
8. **Expand occurrences separately from cursor synchronization.** Keep the existing incremental pull shape for masters, exceptions, and cancellations. Fetch/expand instances only for the configured horizon or the selected series, preserving raw recurrence data and original slot identity. Do not use a date-windowed query with a sync token where Google disallows that combination. Persist expansion completeness separately from the change cursor. A horizon miss is not a deletion. A cursor advances only after the associated change set is durably applied; replay must be idempotent.
9. **Make partial work recoverable.** On startup/manual sync, reconcile target metadata in vault notes against the provider-target index and cached event data. If file creation succeeds but state persistence fails, rediscover by target metadata. If frontmatter update fails, retain the prior link and surface a retryable repair warning. On HTTP 412, fetch the latest instance/series version and present a conflict/retry decision; do not resend stale fields automatically. Keep remote deletion, local note deletion, and disconnect as separate operations.
10. **Migrate conservatively.** Classify a legacy one-off link as an occurrence target and a verified recurring-master link as a series target. An existing link may point directly to an exception ID; resolve its master and original slot from verified provider data before classifying it. Leave ambiguous links unchanged for explicit reconciliation. Migration must be idempotent, preserve body and unrelated frontmatter, and never assign notes by matching titles or dates. Account/calendar changes always use an explicit relink action with old/new target details.

### Test matrix

| Area | Scenario | Expected result |
| --- | --- | --- |
| Identity/idempotence | Create a series note, occurrence note, and day note; repeat each action and retry after restart. Rename a linked file. | One note per target; retries reopen the same note; `calendar_uid` and target key survive rename; paths do not affect identity. |
| Representation mode | For a three-day occurrence, create a whole note, then try to create a day note; test the inverse and two concurrent day-note actions. | Mixed mode is rejected with an actionable choice; concurrent requests produce one note per selected target; separate selected days each have one target/note. |
| Occurrence identity | Move an instance while keeping its Google recurrence slot; compare its `originalStartTime`, remote instance ID, and actual start. | Existing occurrence/day notes remain linked to the original slot, display the moved time, and do not attach to another occurrence. |
| Re-anchor/split | Change the series start; split “this and following” into a new master; remove or alter a formerly generated slot. | Same-master series note stays linked; old occurrence notes with no matching slot become reconciliation-required; new master and new slots get no inherited notes; no title/date matching. |
| Exceptions/cancellation | Cancel one occurrence with a whole note, repeat with day notes instead; cancel the parent series with child notes present. | Only affected targets are marked remote-deleted; bodies and sibling notes remain; parent cancellation warns about child targets without deleting them. |
| Range and day offsets | Move a multi-day occurrence; shrink it below an existing day offset; extend it; explicitly convert between whole and day mode. | Offset suggestions use local civil days and require confirmation; out-of-range day note is preserved and flagged; extension makes no new notes; conversion is previewed and explicit. |
| Timezone/DST/exclusive end | Timed occurrences over spring-forward and fall-back; all-day single/multi-day events with exclusive API end; recurrence timezone differs from display timezone. | Slot keys use recurrence-local identity; day offsets stay on expected local dates; all-day `dateEnd` remains inclusive while canonical end remains exclusive. No fixed-24-hour drift. |
| Cursor/horizon/pagination | First full sync, incremental exception edit/cancel, event outside then inside horizon, multiple instance pages, expired token, page-limit or mid-page failure. | Cursor and cache recover without omissions/false deletes; replay is idempotent; outside-horizon targets are retained; expired cursors trigger full resync; incomplete expansion is marked incomplete, not complete. |
| Offline/retry/version/partial write | Network failure before/after file creation, failed `processFrontMatter`, failed state save, rate limit, and stale ETag/412 on an instance edit. | Retry finds the same target; repair status is visible; no duplicate/orphan note is silently created; 412 refetches and prompts conflict resolution; stale payload is not blindly resent. |
| Files/frontmatter | Rename, move, copy with same UID, copy with new UID but same target, duplicate target metadata, invalid YAML/required fields, unrelated frontmatter and body content. | Rename preserves link; duplicate/invalid records are reported with paths and are not auto-selected or rebound; body and unrelated fields remain byte-for-byte unchanged by metadata updates. |
| Migration/relink | Migrate a legacy one-off link, a recurring master link, a verified exception link, an ambiguous legacy link, and a Google calendar/account move. Run migration twice. | One-off links become occurrence targets; verified master links become series targets; verified exception links retain their original slot. Ambiguous links remain unchanged; second run makes no further changes; account/calendar changes require explicit manual relink. |
| UX/modes | Day-detail series, occurrence, and day actions under disabled, dry-run, import-only, and bidirectional modes; unsupported RRULE; orphan/duplicate warning; month/week and generic Notes projections. | Labels identify the target; import-only permits local notes without Google writes; disabled/dry-run do not mutate; bidirectional instance edit targets that instance; unsupported targets explain why; all attached notes remain out of generic Notes. |
